## The problem

Minibus taxis move most people around in South Africa, but if you're new to a town there's nothing that tells you where a rank is, which taxis run your route, or whether you can flag one down mid-route or have to go back to the rank. That knowledge lives in people's heads: fares, hand signs for specific routes, streets to avoid.

This project tries to put that local knowledge on a map and keep it fresh through the community, not through live tracking.

## What it does

- Shows taxi rank locations and the routes running between them
- Marks whether a route is hailable mid-route or rank-only
- Lets people contribute fares, danger zones, and the hand signs used to hail specific routes
- Uses a Waze-style trust model (votes plus a confidence score) so the data stays honest over time

## What I left out on purpose

No live GPS, no live queue length, no passenger counts. It's one town, not all of South Africa. The value is local knowledge made visible, and building real-time tracking would have buried that. I'd rather ship something small that works than a half-working "Waze for taxis".

## Architecture

```text
React + TypeScript (Mapbox GL JS)
        |
        |  REST (JSON / GeoJSON)
        v
Node + Express API  ──  Mongoose models
        |
        v
MongoDB Atlas (2dsphere indexes)
```

The frontend is a renderer. It fetches GeoJSON from the API and hands it to Mapbox as sources and layers. All the data lives in MongoDB, so I can change what's on the map without redeploying anything.

## Phase 2: replacing hardcoded data with a real backend

In Phase 1 the ranks and routes came from a hand-written JSON file. That proved the visual idea quickly, but every change meant editing code. Phase 2 swaps that file for an Express API backed by MongoDB Atlas.

### Data modeling

Three models: `Rank`, `Route`, and `Report`. Only the first two are fully built right now. `Report` exists as a stub that gets filled out in Phase 3.

```ts
const RankSchema = new Schema({
  name: { type: String, required: true },
  location: {
    type: { type: String, enum: ["Point"], required: true },
    coordinates: { type: [Number], required: true }, // [lng, lat]
  },
});

RankSchema.index({ location: "2dsphere" });
```

Routes follow the same idea, with a `LineString` for the path and references to the ranks they connect.

A few decisions worth explaining:

- **GeoJSON stored natively.** I store locations as real GeoJSON instead of separate `lat` and `lng` fields. Mapbox speaks GeoJSON already, and MongoDB's geospatial queries need it anyway, so there's no translation layer in the middle.
- **A 2dsphere index.** Without it, "which ranks are near this point?" means scanning every document. With it, MongoDB can answer proximity queries properly, which matters once the dataset grows past a handful of ranks.
- **Coordinate order.** GeoJSON is `[longitude, latitude]`, the opposite of what Google Maps shows you. Getting this backwards puts your ranks in the ocean. It was the first bug I hit.

### Seeding

Data goes into the database through a seed script, not by hand in Compass. The script is repeatable: wipe, insert, done. That means I can rebuild the database from scratch at any point, and anyone cloning the repo can do the same.

### API

```text
GET /api/ranks     → all ranks as GeoJSON
GET /api/routes    → all routes as GeoJSON
```

The frontend now fetches from these endpoints instead of importing a static file.

### Phase 2 checkpoint

The test for this phase is simple: rename a rank directly in MongoDB Atlas, refresh the page, and the new name shows up in the map popup. No frontend changes, no redeploy. That's the point at which the map stopped being a demo and became something backed by real data.
